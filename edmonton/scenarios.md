# Edmonton-focused project scenarios

These are synthetic product briefs for discussion. They describe information workflows, not technically approved assemblies or a claim that a particular proposal requires a variance.

## 1. Residential alternative-solution evidence pack

**User:** an Edmonton applicant preparing a residential proposal. **Input:** a fictional proposal, the applicable organizer template, selected source references and two evidence attachments. **Demo:** identify missing project context and one unsupported claim; open the relevant source beside each finding. **Scope:** one submission category and an expert-reviewed checklist.

Acceptance: retain municipality and source version; distinguish missing from present/unverified evidence; flag unsupported citations; export unresolved questions. Validate the package structure with the event's codes reviewers. Use the [codes spec](../specs/building-codes.md) and [process map](process-map.md).

## 2. Exterior assembly documentation navigator

**User:** a builder choosing what documentation to assemble for an Edmonton residential wall/cladding proposal. **Input:** assembly description, product identification and proposed supporting documents. **Demo:** show candidate documentation pathways and missing product-specific evidence. The City's [house-application guidance](https://www.edmonton.ca/residential_neighbourhoods/application-requirements-house-permits) provides locally relevant context for exterior assemblies and engineering/assessment documentation.

Acceptance: exact product and assessment version remain visible; applicability is unverified until reviewed; an uploaded attachment never becomes proof of adequate performance. Do not turn this navigator into an automatic assembly approval engine.

## 3. Point access block reviewer workspace

**User:** a professional team organizing a proposed single-stair building case. **Input:** a permissioned example and City guidance located through the [commercial-building page](https://www.edmonton.ca/business_economy/new-commercial-building). **Demo:** evidence matrix, source navigation and requests for missing information.

This is a more demanding domain example. Restrict a hackathon slice to administrative organization and review usability; fire/life-safety equivalency needs appropriate professional analysis. No technical design or compliance claim is supplied here. Do not assume the guide changes the provincial code or guarantees approval.

## 4. Production home slab/foundation takeoff

**User:** a Landmark estimator reviewing a home-plan baseline. **Input:** organizer-authorized vector PDF and an independently prepared reference quantity. **Demo:** confirm dimensions and thickness; calculate volume; show source anchors; correct one input and recalculate. Only then match a compatible published concrete factor.

Acceptance: footings, walls and slab have explicit boundaries; openings and repeated views are not double-counted; the result is labelled partial until other elements are included. Use the [takeoff method](../docs/drawing-takeoff-method.md) and [carbon spec](../specs/embodied-carbon.md).

## 5. Edmonton plan-family comparison

**User:** a production builder comparing an approved internal baseline plan with an elevation/assembly variant. **Input:** permissioned baseline and revised plan/schedule. **Demo:** retain reviewed geometry, identify changed assumptions, and compare compatible material records.

Acceptance: show what actually changed; invalidate stale quantities; keep product geography visible; preserve module boundary and equivalent function. A mirrored layout alone is not proof that every quantity is unchanged.

## 6. Local permit-context explorer

**User:** a team validating which project categories merit interviews. **Input:** aggregated City building-permit records. **Demo:** compare observed permit-record counts by building type for a stated period. **Output:** interview hypotheses and source links.

Acceptance: count rows as permit records, not homes; distinguish issued permits from starts/completions; disclose missing classifications and query dates. This is supporting discovery, not a replacement for either challenge's core workflow. Use the [tested API recipes](open-data.md).
